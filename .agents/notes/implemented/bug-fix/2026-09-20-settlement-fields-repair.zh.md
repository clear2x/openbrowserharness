# Agent Note：v2 之前的 assistant 结算字段卡死恢复——write open 时就地修复

Status: implemented

[English](2026-09-20-settlement-fields-repair.md) | 中文

## 问题

isSeeded 头部自愈落地后，用户真实档案的下一层遗留形状浮出：发送任何消息都报 `seed assistant/message at index 67 has invalid settlement fields`。format v2 起每个结算都内嵌助手流，种子校验要求非负安全整数 `turn`/`step` 加数组 `stream`；而部署最初几周的构建写的结算没有 `stream`。事件采纳（`validateStoredEvents` 内的 `adoptSessionEvent`）校验消息体但不校验结算字段，于是这种日志畅通无阻地穿过存储契约、只在恢复种子校验时被拒——面板渲染历史一切正常，一到 `ensureAgent` 每次发送必死。把事件标成 `ignorable` 也不行：种子循环对每个事件都做校验且要求 seq 连续，已知类型的坏载荷必须真正变合法。

## 决策

`@deepseek-ai/dsh-session` 现在导出 `assistantSettlementFieldsValid`——种子校验强制的那条判定的唯一权威——IndexedDB 修复共享它而不是复述契约。修复过程（`repairLegacyUnknownArtifact`）对已知类型的结算就地规范化：非法的 `turn`/`step` 逐个沿用前一个结算的值（保持生命周期序列合理），非数组的 `stream` 变成空记录，其余 data 成员原样保留。(b) 写开触发器在结算扫描上同样触发（与坏头部、外来类型并列），所以带时代结算的当前代日志在第一次恢复时就地修复；采纳仍然拒绝一切规范化无法诚实修复的消息体形状，那种失败走既有 catch 整体隔离。原始行永远先原样归档，修复后的代在后续打开时不再触发（不重复修复）。

## 考虑过的替代

- **把非法事件标成 `ignorable`。** 否决：种子循环校验每个种子事件且要求连续性，该标记对已知类型的坏载荷毫无作用。
- **在第一个非法事件处截断日志。** 否决：非法结算位于活跃会话日志中部，截断会连带丢弃其后所有更新的合法事件。
- **对当前代重跑完整迁移链。** 否决：迁移链管相邻版本搬运；本部署自身时代漂移的载荷规范化属于已武装的修复，与其之前的头部、外来类型抢救同列。

## 后果

- 恢复不再死在时代结算上：第一次发送就地修复该代（原件留档），回合继续。
- 结算契约只剩一个定义，种子校验与修复共享。
- 覆盖：导出的判定对着种子校验的拒绝矩阵做单测；IndexedDB 套件把带 v2 前结算的 68 事件当前代日志推过 write open——结算规范化、原样归档、重开幂等——真机复现装置按同一日志播种、发送用户原话、看着回合无错跑完。
