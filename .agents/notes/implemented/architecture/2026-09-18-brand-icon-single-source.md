# Agent Note: Brand icon single source — open-orbit mark, generated derivatives, build gate

Status: implemented

English | [中文](2026-09-18-brand-icon-single-source.zh.md)

## Problem

The extension shipped two tracked icon sets that had already drifted: `apps/extension/public/icons/` (the set the manifest references) and `apps/extension/icons/` (a stale second copy whose preview.md still claimed the manifest was unwired). The website favicon was a third byte copy with no sync mechanism. PNGs were hand-rasterized with two competing documented tools (`rsvg-convert` in one comment, a temporary `@resvg/resvg-js` install in the other), so editing the SVG silently left stale PNGs. The mark itself — a glassy blue tile with a large system cursor — read dated next to the product's flat UI and lost its shape at the 16px toolbar size.

## Decision

One vector source, one mark everywhere: `apps/extension/public/icons/icon.svg` is the only brand artwork source. The mark is an open orbit and a page-driving pointer — the ring supplies the O of OpenBrowserHarness and the pointer occupies the ring's upper-right break, so the two shapes read as one gesture at 16px. It is flat by construction: `#172554` tile, `#67E8F9` orbit, `#F8FAFC` pointer, no gradients, filters, or glass effects, with geometry sized for the toolbar (8px stroke becomes exactly 1px at 16px).

- `apps/extension/scripts/generate-icons.mjs` renders the committed derivatives (`icon16/32/48/128.png`) with the lockfile-pinned `@resvg/resvg-js` devDependency and rewrites `website/public/favicon.svg` as a byte copy of the source. `generate:icons` writes, `check:icons` (`--check`) fails on any drift, and the extension `build` script runs `check:icons` first.
- The SidePanel welcome glyph renders that same file as an `<img>`; the separate inline `OrbitPointerIcon` drawing is deleted, so the panel, the toolbar, the extension management page, and the docs site share one mark.
- The drifted `apps/extension/icons/` directory is deleted; git history retains the old artwork.

Coverage: `apps/extension/tests/brand-assets.spec.ts` pins the manifest's icon mapping, the four PNG headers (dimensions, 8-bit RGBA), the favicon/source byte equality, and the build-gate wiring; `caps-css.spec.ts` follows the welcome glyph's move to artwork (the dark-mode ink flip now covers only the send arrow).

## Alternatives considered

- **`rsvg-convert` as the documented renderer (the old SVG comment).** Rejected: it is not a declared dependency and is absent from Windows and most CI runners; a lockfile-pinned renderer makes the committed bytes reproducible everywhere.
- **Keeping the second `icons/` directory as design history.** Rejected: its preview.md contradicted the wired manifest and nothing would have noticed further drift; git history already preserves the old artwork.
- **Manifest icons as SVG only.** Rejected: Chromium's extension icon surfaces expect raster sizes, and the four-size PNG set is the contract the manifest and stores already speak.
- **A separate favicon source for the website.** Rejected: a second source is exactly the drift that occurred; the favicon is a regenerated byte copy, never hand-maintained.

## Consequences

- Editing the SVG without running `generate:icons` fails the extension build and the brand-assets spec with a stale-derivative error instead of shipping old artwork.
- `@resvg/resvg-js` is a devDependency only; the shipped extension bundle is unchanged in kind, and the manifest keeps referencing the same four PNG paths.
- The welcome-glyph foreground no longer participates in the dark-mode ink flip (artwork, not a `currentColor` glyph), and its holder contributes only a soft host-side shadow.
- `docs/assets/sidepanel-welcome.png` was re-captured from the real `SHELL_CSS` markup with the new mark; future mark changes ride the same file, so the welcome UI needs no re-shoot, though screenshots showing the tile age with the brand.
