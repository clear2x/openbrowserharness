# Agent Note: 不直接请求站点接口

Status: implemented

[English](../2026-11-24-no-direct-site-api-requests.md) | 中文

## Problem

第一条规则（[网站任务通过真实页面操作完成](2026-11-24-website-tasks-through-page-operations.md)）堵住了模型自己写出来的出口——调用站点接口的页面脚本——却把另外三个出口留给了提示词：用标签页打开接口地址、`web_fetch` 抓接口地址，以及 `video_index` 的 index 动作（它带着用户的登录态请求 B 站的视频、字幕与音频端点）。这条规则的理由比那篇笔记写的更尖锐。网站分辨得出一个不是它自己的页面发出的请求——缺签名、本该是 XHR 的位置来了导航、机器般的节奏——并以风控回应；在用户登录的账号上，这可能导致封号。提示词保护不了账号：破坏它的那一次，请求已经发出去了。还有一句提示词在跟规则作对：`page_network` 的描述教模型找出数据端点，再用 `page_evaluate` 去 fetch 它们。

## Decision

凡是 agent 能触发的直接请求，一律不请求站点的接口，除非用户打开了那一个开关。

工具闸门（`chrome-tool-gate`，即 `tools/pre-execute` 瀑布）在每一种权限模式下都在这类调用执行之前拒绝它：

- 点名了请求原语、或写出了接口地址的 agent 自写代码——把它赋给 `location.href`、打开它、设为元素的 `src`：第一条规则的词法检查，加以扩展；
- 地址是接口地址的调用：`tabs_open`、`page_navigate`、`page_batch_actions` 的 `navigate` 步骤、`web_fetch`；
- `video_index` 的 `index` 动作。

满足下列任一条即为接口地址：首个主机标签是接口主机——`api`、`apis`，或把二者之一作为完整词段携带的标签（`open-api`、`h5api`、`api2`）——除非该子域是文档站（`api.flutter.dev`、`api.dart.dev`、`api.jquery.com`、`api.rubyonrails.org`、`api.wordpress.org`、`api.kde.org`）；或者首个路径段是任意站点上的接口根（`api`、`apis`、`ajax`、`graphql`）；或者它是某个站点家族放在页面主机下的接口根（`bilibili.com` 下的 `x`）。其余都是页面地址，放行。判定函数是 `shared/script-network.ts` 里的 `isSiteApiUrl`。

对没有索引的视频，`video_index` 保留一条页面操作路径：`zoom` 接受视频页 URL 代替索引键。它打开页面、把真实播放器定位到该时刻并截取画面帧，同时用本地 OCR 读取烧录字幕；没有任何请求发往 B 站接口。`query`、`status`、`list`、`remove` 读取已存的索引，不设闸。

`page_network` 的描述不再教端点路线。这个工具被描述为对页面自身请求的被动捕获，用于理解页面；捕获到的地址不是让 agent 去请求的。

开关是内置能力「直接请求站点接口」；存储键 `dsh-capability-script-network` 保留了它只覆盖页面脚本时得到的名字，已存下的选择因此不会丢。开关的描述写明风险，每条拒绝文案都写明风险，而唯一需要这个开关的技能 `site-api-crawl` 要求模型在开始之前先把风险讲给用户。

### 规则之外

被动观察不是请求：`page_network` 读取的是页面自己发出的内容，而 agent 打开的页面会用它自己的签名发起它自己的接口调用——这就是一个人打开页面。页面地址不设闸，包括内嵌了接口响应的页面。`/learn-site` 自己抓取同源的页面源码；它请求的是页面，不是接口。用户自己配置的 MCP 服务器的工具属于用户，不设闸。

## Alternatives considered

**让导航与 `web_fetch` 留在提示词规则之下**——上一篇笔记的决定。学会了这条路线的模型不会理会那行字，而标签页导航正是在反常的 `Sec-Fetch-Dest` 之下携带用户 cookie 的那个出口。相对于封号，代价太大。

**不带文档站例外的主机规则。** `api.flutter.dev` 与 `api.jquery.com` 是给人读的文档站；拒绝它们会把用户推向那唯一一个会关掉保护的开关。六个主机被豁免。第七个文档站是一次带清楚说明的拒绝，而不是一个发出去的请求。

**为每个平台各写一条路径规则**（抖音的 `/aweme/`、淘宝的 `/h5/`）。每一条都是对某个站点路由的猜测，会在它下一次改版时无声地失效。主机规则与通用路径根已经覆盖模型会写的拼法；B 站的 `x` 根保留，因为它是本 fork 的首要目标站点。

**把检查放进每个工具里**——`web_fetch` 自己读自己的 URL，`video_index` 自己读开关。那样规则就要分布在四个地方、配四套拒绝文案。由一个监听器拥有规则、拒绝文案与开关。

**移除 `video_index` 建索引。** 在没有端侧录音的情况下，这条通道是得到全片台词索引的唯一途径，想要它的用户可以在知情的前提下接受风险。它留在开关之后；按 URL 的 `zoom` 是页面操作路径。

**用被动读取响应体取代接口数据**——给 `page_network` 扩展 `Network.getResponseBody`，把页面自己的请求产生的数据交给 agent。没有做：捕获层目前返回的是请求清单，而保留哪些响应体、保留多久、模型可以读什么，本身就是一个决定。如果用户在这条规则下怀念接口数据，这是下一步该做的事。

## Consequences

代价：在用户打开开关之前，`video_index` 建索引是关闭的——一个已发布功能的主要动作现在需要显式选择，商店文案也照此说明。地址判定是启发式的：某个没人列出的路径根下的平台接口能通过闸门（提示词规则仍然禁止它，但再没有别的手段）。六个之外、从 `api` 主机提供服务的文档站会被拒绝，文案里指明开关。页面脚本只要写出了接口地址就会被拒绝，无论它想拿它做什么——比如读取页面自身接口请求的资源耗时；这件事该用 `page_network`。

换来：agent 能触发站点接口的出口没有一个默认敞开，包括本 fork 自己发布的那个。规则的理由——风控与账号——写在指引、每条拒绝文案和开关描述里，解除规则的用户是知情地这样做。

测试：`tests/script-network.spec.ts` 固定地址判定（接口主机、词段标签、路径根、文档站例外、页面地址、非 HTTP 协议）、三条拒绝文案，以及开关名称与面板的一致；`tests/tool-gate.spec.ts` 固定闸门对每个出口、各类放行调用与开关的行为；`tests/video-index-zoom.spec.ts` 固定无索引时按 URL 的 `zoom`；真机探针 `script-gate-probe` 用 mock 模型在真实引擎组合上跑这些出口。
