# Agent Note：会话删除——持久层行删除、列表墓碑、两段确认

Status: implemented

[English](2026-09-21-session-delete.md) | 中文

## 问题

历史会话只能重命名不能删除，切换器只会越积越多。新会话启动改动让旧对话变成纯可选历史之后，用户明确提出要能删除。

## 决策

三层各司其职：

- **持久层**新增 `SessionPersistence.delete(id)`：单个原子事务删掉身份行、事件区间和任何归档代。未知 id 是无操作（删除重试保持正确）。基类默认拒绝，后端实现该方法即声明支持——目前只有扩展挂载的 IndexedDB 后端实现。
- **桥**新增 `session.delete`：运行中的会话拒绝（先中断——在活回合下方删除会和回合自身的追加赛跑）；其余删除持久行并把 id 加入内存墓碑集合。处置活 agent 是创建者拥有的 handle 能力（session-main 这类配置创建的 agent 归 loop 纤程所有、按设计不暴露 handle），所以删除后仍在内存的会话由墓碑集在本引擎生命周期内从 `session.list`/`session.search` 隐藏；重启后它背后没有任何持久行。
- **面板切换器**：每行获得删除入口，两段确认（第一下武装并变警示红，第二下删除；其它交互解除武装）。删除活跃会话回落到新会话哨兵，且哨兵的历史读取改为清空转写而不是保留上一段对话文本（否则「读取失败保留文本」规则会把已删内容留在屏幕上）。

## 考虑过的替代

- **删除时处置活 agent。** 否决：处置是所有者的 handle 能力；配置创建的 agent 从不暴露 handle，注册表级处置会为单个 UI 功能切过有文档的所有权模型。墓碑以用户可见的结果达成目的。
- **用模态对话框确认。** 否决：切换器本就用行内操作（重命名铅笔）；就地两段确认符合该习惯，无需新增浮层管线。

## 后果

- 删除会话立即从切换器消失、从 IndexedDB 持久消失（身份、事件、归档）。删除活跃会话落到全新开始。
- 运行中的会话响亮拒绝，而不是和自己的事件流赛跑。
- 覆盖：IndexedDB 套件断言三行全删加幂等；真机装置播种两个会话，删非活跃（切换器与磁盘皆无），再删活跃（面板回落新开、墓碑保持隐藏、磁盘干净）。
