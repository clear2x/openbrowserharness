# Agent Note：面板打开即新会话；运行中的会话与历史都靠显式选择

Status: implemented

[English](2026-09-21-boot-fresh-session.md) | 中文

## 问题

面板每次打开都采纳最新的持久会话——永远是 `session-main`——用户被扔回一个从没主动要打开的旧对话（还往往很重）。`＋ 新会话` 按钮一直都在，但默认流程和自然预期对着干：打开 → 开始新任务；继续旧对话应当是显式选择。更糟的是，自动恢复正是每次重载都要付冷恢复（和一次性修复）成本的原因。

## 决策

外壳以哨兵新会话 id 启动（`session-new`，形状上与 `mintSessionId` 的 `session-<uuid>` 输出永不碰撞）。启动不再采纳最新会话：`session.list` 只用来采纳启动时刻**仍在运行**的会话，让进行中的工作不会被丢在切换器后面。哨兵会话纯客户端——第一次发送之前不在服务端落任何东西：`promptSend` 先 `session.create`，采纳铸造出的 id（转写、重试芯片、切换器都以它为准），再投递提示词。于是打开面板永远不会往切换器里塞空行：没发过消息的新开视图不留任何痕迹。预热跳过哨兵（没有持久物可暖），各会话读取（历史、用量、权限、状态）对未知 id 退化到既有的空/默认姿态。

## 考虑过的替代

- **启动时就铸造真会话。** 否决：每次打开都会给切换器加一行无标题会话——用户不发消息时纯属垃圾。
- **保留自动恢复但加速。** 否决：用户要的是行为改变，不只是速度；新开同时也把每次打开的自动冷恢复成本清零了。
- **删掉运行中采纳分支。** 否决：四行安全网而已。实际上重载面板会中止进行中的回合（客户端离开即中止是引擎的既有语义），该分支很少触发，但一个熬过快速重开的回合必须保持可见。

## 后果

- 打开 → 欢迎示例的新对话；旧对话只能经切换器显式选择到达。
- 第一次发送铸造恰好一个真会话；空开不留痕。
- 覆盖：真机装置播种旧持久会话，打开面板（旧转写不出现），在新视图上发送（回合跑完；IndexedDB 恰好新增一行会话），回合中重载（面板照样新开；被中断的对话保持持久可手选）。扩展全量、typecheck、lint 全绿。
