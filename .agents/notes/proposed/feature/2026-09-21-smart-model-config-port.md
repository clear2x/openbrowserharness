# Agent Note: Smart model config — port ZCode's layered provider/model knowledge base

Status: proposed

English | [中文](2026-09-21-smart-model-config-port.zh.md)

## Problem

Adding a model to a provider route today is fully manual. The installed `@earendil-works/pi-ai` catalog supplies defaults only for exact ids it happens to know; any other model id — a renamed upstream, a gateway alias, a beta suffix — must have `contextWindow`, `maxTokens`, input modalities, and reasoning efforts declared by hand in the route's `models`/`modelOverrides` (`packages/llm/llm-pi-ai/src/catalog.ts`). Three gaps follow from that:

- **Unknown ids get nothing.** Exact-id lookup cannot express "ids ending in `[1m]` have a 1M context window" or "on `openai-completions` endpoints at this base URL, `claude-*` accepts mid-conversation system prompts". The facts exist but have no carrier.
- **The knowledge base moves at npm-release speed.** pi-ai's catalog ships with the dependency. A provider that changes a capability today is wrong until the next upgrade; there is no remote, rev-friendly update path.
- **The editor has no recommendation surface.** The settings UI renders the namespace schema as bare fields with no notion of "here is the recommended value; typing over it makes it yours" — the user cannot tell an inherited default from a value they must choose.

The ZCode workspace (sibling checkout `../ZCode`) ships a design that solves all three: a layered regex rule engine, a remotely-updatable signed-shape release with bundled/LKG fallback, and a "smart config" editor where recommended values appear as placeholders and any manual edit converts that one field to a personal override. This note port that design into the harness, reusing the pi-ai profile shape as the rule payload so the two knowledge sources stay compatible.

## Proposal

Port four pieces, mapped onto existing dsh structures. The rule payload is a `PiAiModelProfile`-shaped overlay (already `Omit<..., 'id'>`-able via `PiAiModelOverride`), so a resolved recommendation feeds the existing materializer without a parallel config type.

## Porting manual

Numbered phases; each ends with a verify step. ZCode paths are relative to the sibling checkout `../ZCode` and were read from the working tree; re-check line anchors if that tree has moved.

1. **Read the source in this order.** `model-config.ts` (`ModelConfigRules.resolve` — the whole engine is ~40 lines: exact rules match `providerId+modelId`, then `template-model`, then regex rules gated by `apiTypeMatch`/`baseUrlMatch`, all overlaying leaf-by-leaf in order); `rule-data-schema.ts` (the pattern `z.string().refine(new RegExp('^(?:'+p+')$'))` compile check and the smart/manual mutex `superRefine`); `zcode-builtin-release.ts`; `useModelConfigResolution.ts` + `useProviderModelDraft.ts` + `ProviderModelDraftState.ts` (the UX state machine); `facades.ts:239-298` (the two resolve input shapes). Verify: you can state, without re-reading, why a manual rule `clearManualModelConfig`s the composed result before overlay (system leaves must not leak into a fully-manual config).
2. **Scaffold `packages/llm/llm-model-rules`.** Follow `docs/cookbook/adding-a-package.md`. Contents: overlay primitives (or reuse the repo's existing deep-merge JSON helpers — check `packages/util` first), the rule types, `ModelRules.resolve({ route: { provider, api, baseURL, modelId } })` returning a `PiAiModelOverride`-shaped partial, the release codec, and the schema gates. Verify: `pnpm typecheck` and `pnpm lint` pass; unit tests cover ordered overlay, case-insensitive regex, baseUrl normalization (trailing slash, default port), invalid-pattern rejection, and the smart/manual mutex.
3. **Seed the bundled release.** Write a one-shot script that walks `getBuiltinModels()`/`getBuiltinProviders()` from `@earendil-works/pi-ai/providers/all` and emits rule data (one exact `model` rule per catalog model id is sufficient as a seed; add hand-written regex rules afterward for the suffix conventions pi-ai's ids don't cover). Bundle the JSON inside the package; never fetch at module load. Verify: the script is idempotent (byte-identical output on re-run) and the bundled JSON passes the release codec round-trip.
4. **Wire the resolver into `llm-pi-ai` config resolution.** In `catalog.ts`, when a route names a model the installed catalog does not know, resolve through the rule engine (route `api`/`baseURL` + model id) before falling back to route defaults. Stored reads keep deferring — a rule miss yields diagnostics, not a hard failure, exactly as today. Verify: existing `llm-pi-ai` tests stay green; new tests pin that rule-resolved recommendations never override an explicit user field.
5. **Expose the resolve seam over Remote.** Next to the `llm-pi-ai` settings namespace, add a resolve operation taking `{ routeKey, modelId, personalDraft }` and returning `{ recommended: PiAiModelOverride, effective, issues }` — the two input shapes from ZCode collapse into one here because a route already carries `api`/`baseURL`. Reads run against the applied release snapshot; never mutate settings from a resolve. Verify: the API gateway Typert contract builds and the operation is reachable from the client face.
6. **Port the remote update loop.** Cordis service, started at boot: fetch control plane → CDN (https-only, credentials-omit, no redirects, bounded by the repo's timeout utilities), decode the release, atomically write the LKG file, re-resolve affected routes, emit a cordis event the settings UI already listens to for refresh. Config: endpoint + interval live in a settings namespace (secret-free); failure backoff mirrors ZCode's 60 s → 1 h cap. If dsh ships single-process, drop the lease file and keep the backoff state in memory; do not port machinery the process topology does not need. Verify: kill the network mid-run — the harness keeps the last-good release and the failure is logged, not thrown into the request path.
7. **Port the smart-config editor UX.** In the web settings form for `llm-pi-ai`: recommended values render as input placeholders (never values); touching a field marks that path in the namespace's `user` section (the settings seam already treats user-section presence as the override marker — reuse it rather than adding an `overriddenFields` twin); a 1.2 s idle trigger schedules resolve, blur/Enter flush it; an in-flight resolve is guarded by a generation counter and an identity object so `A→B→A` never replays a stale response; a matched resolution shows transient feedback; a restore action re-resolves from the current draft. Verify: race tests — type `a`, `ab`, then back to `a` quickly and assert the final placeholder reflects the last generation only.
8. **Add the route-preset picker.** On route creation, offer release-declared templates (name map, protocol, base URL) before the bare form; choosing one prefills the route's `api`/`baseURL`. Verify: creating from a template and typing an id the rules know yields a fully-populated recommendation without touching a schema field by hand.

Run `pnpm check:all` before opening the PR; write the `implemented/` counterpart of this note in the same change, folding this manual's plan sections into present-tense reality per the note-move rules.

## Alternatives considered

- **Keep hand-declared profiles plus the pi-ai catalog only (status quo).** Lost: every fact about ids the installed catalog does not know, and any update path faster than npm. The catalog stays — it becomes the seed layer of the release — so this alternative is really "freeze the base layer".
- **Discover capabilities from provider APIs (`GET /models` etc.) at configure time.** Lost: the endpoints enumerate ids, not capabilities; the shapes are provider-specific; and the flow then requires network access and live credentials just to fill a form. ZCode's static rules encode audited facts, which is also what makes them reviewable in a diff.
- **Extend pi-ai itself instead of adding a rule layer.** Rejected: pi-ai is a vendored third-party surface (`@earendil-works/pi-ai`), its catalog updates at dependency-upgrade speed — the exact limitation this feature removes — and remote-config concerns do not belong in a generic adapter library.

## Acceptance criteria

- A user adding a model id the installed catalog does not know, on a route with a known protocol/base URL, sees recommended `contextWindow`, `maxTokens`, modalities, and reasoning efforts as placeholders within ~1.2 s of stopping input, without any hand-declared field.
- Editing a recommended field converts only that field to a user override (settings `user` section), while untouched fields keep following release updates; toggling smart mode off pins all currently recommended values without discarding in-progress edits.
- The harness ships a bundled release; a refreshed release changes recommendations without an app upgrade, and a failed fetch leaves the last-good release serving with a logged warning.
- Two routes with the same model id but different `api`/`baseURL` can resolve different recommendations for that id (the `model-api`/`provider-site` rule tiers are observable end to end).
- Rule data with an uncompilable regex pattern or a smart/manual conflict for one provider+model is rejected at the boundary with a named issue, and unrelated models keep serving.

## Risks

- **Regex safety.** Rules are remote-supplied patterns compiled with `new RegExp`. Mitigate at the boundary: the compile check plus a length cap and a reject-list for nested quantifiers (or a safe-regex scan) before a release is applied; document that matching runs per keystroke-settle, not per keystroke.
- **Two knowledge sources, one answer.** pi-ai's installed catalog and the release can disagree (e.g. the catalog says 128k, the release says 200k). The precedence rule is fixed — explicit user field > release rule > installed catalog > route defaults — and must be stated in both this package's README and the `llm-pi-ai` config docs; drift in that statement is the failure mode to guard in review.
- **Remote config is an attack surface.** The release changes request-shaping behavior. Keep the control-plane fetch credential-free, the CDN URL https-only and redirect-refusing, the codec schema-strict, and record a rejected-release path that falls back to bundled/LKG rather than empty.
- **UX surface growth.** The placeholder-as-recommendation pattern assumes the settings form can distinguish "placeholder from recommendation" from "placeholder as hint". The existing form uses placeholders as static hints today; the port must migrate those fields, not stack two meanings on one attribute.
- **ZCode coupling.** The seed must not import ZCode's provider ids (`builtin:*`, templates) — they are meaningless here and a wholesale copy would ship dead rules. The conversion script in phase 3 is the boundary.
